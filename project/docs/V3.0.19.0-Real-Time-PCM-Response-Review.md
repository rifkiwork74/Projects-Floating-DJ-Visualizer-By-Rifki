# Floating DJ Visualizer V3.0.19.0 — Real-Time PCM Catch-Up & Response Review

## Baseline and scope

- Baseline: V3.0.18.9 (`versionCode 104`).
- Output: V3.0.19.0 (`versionCode 105`).
- Target path: user-authorized MediaProjection playback capture when M.Projection is ON.
- Main goal: prevent the visualizer from rendering an old PCM backlog and make Response 41% react sooner while preserving the existing low/mid/high frequency mapping.

## Findings in V3.0.18.9

### 1. Hop cadence was not an end-to-end latency guarantee

At 44.1 kHz, Hop 256 represents 256 / 44100 = **5.80 ms** between adjacent analysis windows. FFT 4096 represents a **92.88 ms** analysis window with **10.77 Hz/bin** resolution. The code advanced the window by one Hop and calculated a complete stereo FFT before reading the next Hop.

If analysis or scheduling took longer than one Hop, PCM data could accumulate in AudioRecord's buffer. The next blocking reads would then return older queued samples immediately. That can make the output appear to lag even though the configured Hop is 256.

The three active Floating layers do not each run their own FFT. One shared spectrum frame is delivered to all visible layers. Their per-layer mapping and rendering are separate, but the PCM FFT is shared.

### 2. Response smoothing assumed a legacy 20 Hz capture interval

Both FloatingVisualizerService and MainActivity converted a 20 Hz reference factor into display-frame smoothing. At Response 41%, the old curve corresponds approximately to:

- Attack time constant: 38.8 ms.
- Release time constant: 82.6 ms.

The same time constant was then evaluated at 60/90/120 Hz, which was stable across refresh rates but too soft for the requested fast beat response.

## V3.0.19.0 changes

### 1. Sample-exact catch-up in the MediaProjection worker

The worker now:

1. Reads one complete Hop using a blocking read.
2. Moves that Hop into the rolling 4096-sample PCM window.
3. Checks for already-buffered PCM using non-blocking reads.
4. Moves every complete queued Hop into the same rolling window, preserving sample order and any partial Hop for the next blocking read.
5. Runs the stereo FFT once on the newest complete window rather than calculating and publishing every stale intermediate window.

The catch-up drain is bounded to 64 extra Hops per pass to avoid an unbounded drain loop. No samples are intentionally skipped from the rolling PCM history; only intermediate FFT calculations/publications are skipped when the worker has fallen behind. If no backlog exists, the worker continues to publish at each Hop.

### 2. Faster time-based attack and release

The shared response curve now uses direct time constants instead of assuming 20 Hz capture:

| Response | Attack time constant | Release time constant |
|---:|---:|---:|
| 0% | 24.0 ms | 52.0 ms |
| 41% | 16.6 ms | 38.9 ms |
| 100% | 6.0 ms | 20.0 ms |

The per-frame interpolation is `1 - exp(-deltaTime / timeConstant)`, so the effective time behavior remains consistent across 60/90/120 Hz panels. MainActivity Live Display and Floating rendering use the same equation.

### 3. Kept unchanged on purpose

- FFT size and Hop selection, including FFT 4096 / Hop 256.
- Stereo L/R PCM transforms and RMS magnitude combination.
- Dedicated 256-band Single/DJ frequency bank and per-profile Hz range selection.
- Horizontal 64-band log map and full-bin measurement.
- Existing fixed PCM calibration scales and the Visualizer route's scaling behavior.
- Existing floating profile/scene data and layer configuration.

No frame-peak, content-dependent, or whole-spectrum gain normalization was added. A selected 55–62 Hz interval is narrower than the 10.77 Hz bin spacing of a 4096-point FFT at 44.1 kHz; the existing range sampler uses the actual bin-width metadata rather than claiming a true 7 Hz resolution.

## Expected result and limits

- When the analysis worker can keep pace, the newest target is still generated on each 5.80 ms Hop.
- When the worker falls behind, it catches up to the newest PCM window instead of steadily rendering queued old FFT frames.
- Response 41% rises and falls more quickly than in V3.0.18.9, with the same curve in Live Display and Floating layers.
- 5.80 ms is the PCM analysis step, **not** a promise of 5.80 ms glass-to-glass visual latency. The UI is still rendered on display frames (16.7 ms at 60 Hz), and a 4096-point window spans 92.9 ms. Preserving that long window is intentional for low-frequency resolution.

## Android API compatibility basis

The worker uses the `AudioRecord.read(short[], offset, size, readMode)` overload with `READ_NON_BLOCKING` only while draining already-buffered samples. Android documents this overload as available from API 23; non-blocking reads return immediately with the amount currently available, including zero when no data is ready. The app's minimum SDK is 26, so the API is within the declared platform range. Partial reads are retained until a complete interleaved Hop is assembled. See the [Android AudioRecord API reference](https://developer.android.com/reference/android/media/AudioRecord).

## Diagnostics added

Every five seconds, `FloatingDJ.Audio` reports a `PCM live` line containing:

- `batchHops`: number of complete Hops included in the latest rolling window before analysis.
- `hop`: configured Hop interval in milliseconds using the actual recorder sample rate.
- `publishInterval`: interval between published FFT results.
- `analysis` / `avgAnalysis`: current and smoothed FFT analysis cost.
- `drainLimit`: whether the 64-Hop catch-up bound was reached.

These values should be captured on the target Redmi device while playing the same track and settings. They distinguish a healthy 5.8 ms read cadence from actual processing or scheduling bottlenecks.
