# V3.0.18.2 — Audio Source Parity & Android Capture Compliance

## Scope

This update improves consistency between the two existing audio input routes. It does not add a microphone input mode, does not change the Equalizer DSP, and does not attempt to capture applications that disallow playback capture.

## The two routes in this project

```text
M.Projection OFF
Other apps' permitted system playback
  -> Android Visualizer(0), output-mix session
  -> device-reported FFT capture size and callback cadence
  -> 8-bit packed FFT data
  -> 64-band logarithmic spectrum
  -> shared time-based response smoothing

M.Projection ON (Android 10+)
Other apps' playback that is eligible for capture
  -> user-approved MediaProjection
  -> AudioPlaybackCaptureConfiguration
  -> stereo-first AudioRecord PCM (mono fallback only if stereo cannot initialize)
  -> separate L/R Hann FFTs
  -> RMS magnitude combination after FFT
  -> calibrated 64-band logarithmic spectrum
  -> shared time-based response smoothing
```

**Important:** M.Projection OFF is not microphone capture. The current project attaches `Visualizer(0)` to Android's global output mix. A separate microphone analyzer would be a distinct feature with its own explicit microphone UI, permission, foreground-service type, and privacy disclosure; it is intentionally not introduced here.

## Why the routes can feel different

### Visualizer output mix

- `Visualizer(0)` observes the global output mix; it is not attached to a single player's audio session.
- Its capture size must be a power of two within `Visualizer.getCaptureSizeRange()`; therefore a requested FFT size is not necessarily the applied size on every device.
- The callback cadence comes from `Visualizer.getMaxCaptureRate()` and the implementation / audio HAL. The app logs the requested and applied capture size, reported callback rate, sample rate, FFT bin spacing, and window duration.
- The project explicitly requests `SCALING_MODE_NORMALIZED`, which is the platform's music-visualizer mode. The SDK describes this mode as scaling based on captured content; `SCALING_MODE_AS_PLAYED` instead tracks playback volume.
- Hop Size does not control this API. The callback cadence is platform-controlled.

### MediaProjection playback capture

- `AudioPlaybackCaptureConfiguration` is available from API 29 (Android 10).
- The capture is built with `AudioRecord` and PCM data. The project requests 44.1 kHz PCM16 and reads the configured `AudioRecord.sampleRate` back for all bin/time calculations. This is the recorder sink rate selected by the builder; it is not a promise that the source player natively mixes at 44.1 kHz.
- The project prefers stereo. Left and right are transformed independently; their magnitudes are combined after FFT using RMS energy. This avoids cancellation that can occur when anti-phase L/R audio is averaged into mono before FFT.
- Hop Size determines how many new PCM frames are accumulated before the FFT window advances. The reader now fills an entire Hop block even if the platform returns partial reads.
- The capture route is not universally available for every player. The source player must use an eligible audio usage (`USAGE_UNKNOWN`, `USAGE_MEDIA`, or `USAGE_GAME`), its effective capture policy must allow capture, and it must satisfy the platform's manifest / target-SDK rules. Capture is also restricted to the same user profile.

## V3.0.18.2 calibration changes

### 1. Shared band measurement

Both sources retain the same 64-band logarithmic frequency map and the same `measureLogBandMagnitude` routine. Each band uses the FFT bins inside its frequency interval, RMS magnitude, and peak retention. Narrow intervals below one-bin width use fractional interpolation.

### 2. PCM peak normalization

The output-mix Visualizer route requests the platform's normalized scaling mode. To narrow the perceived level difference, the PCM route now applies a single bounded frame-peak gain to the complete interleaved PCM analysis window before the per-channel Hann FFT. The same gain is applied to L and R; it does not alter the stereo phase relationship.

The normalization is bounded (`48x`) and skips near-zero frames below a small silence floor. This reduces the chance that a near-silent buffer or tiny noise floor is expanded without limit. It is an approximation of the Visualizer's normalized behavior, not a claim of bit-identical platform DSP.

### 3. Common display calibration

For a Hann window, the coherent magnitude of a bin-centered full-scale sine is approximately `N/4`. The PCM path now uses a calibration factor of `5.08 = 4 * (127 / 100)` before the shared square-root display curve. This maps the PCM magnitude to the approximate 8-bit scale used by the Visualizer path. Device-side Visualizer implementations can still differ, so some output-level variance is expected.

### 4. Fixed Hop progression

`AudioRecord.read()` can return fewer samples than requested. Instead of treating every partial return as a full analysis step, the capture thread now accumulates samples until one complete `hopSize * channelCount` block is available. The FFT window then advances by exactly `hopSize` frames. This makes the configured Hop interval meaningful and keeps stereo interleaving aligned.

## Android 8–16 compatibility and privacy matrix

| Android version | M.Projection OFF | M.Projection ON |
|---|---|---|
| Android 8–9 (API 26–28) | Android `Visualizer(0)` output-mix route, subject to permission and OEM implementation | Not available: `AudioPlaybackCaptureConfiguration` starts at API 29 |
| Android 10–13 (API 29–33) | Android `Visualizer(0)` output-mix route | User-approved playback capture through `MediaProjection` + `AudioRecord`, subject to source-app eligibility and capture policy |
| Android 14 (API 34) | Same output-mix route | Requires the declared `mediaProjection` foreground-service type/permission and user consent for each new MediaProjection capture session; projection lifecycle callbacks must be handled |
| Android 15–16 (API 35–36) | Same output-mix route | Retains MediaProjection consent / foreground-service requirements. Android 15+ does not allow launching a mediaProjection foreground service from `BOOT_COMPLETED`; this app starts capture through an explicit user action, not boot auto-start |

### Playback-capture eligibility rules

Android documents that an app's playback is capturable only when all applicable conditions are met:

- The playback usage is `USAGE_UNKNOWN`, `USAGE_MEDIA`, or `USAGE_GAME`.
- The effective capture policy permits capture (`ALLOW_CAPTURE_BY_ALL`); the most restrictive policy wins.
- The source app's manifest and target-SDK behavior permit playback capture.
- The capturing and playing apps are in the same Android user profile.
- The user grants the MediaProjection request and the app has `RECORD_AUDIO`.

This application must not circumvent any of these conditions. If a source app denies capture, the valid behavior is to show no captured signal or fall back to the separate Visualizer route—not to switch to microphone capture silently.

## What remains platform-dependent

- Some OEM audio HALs restrict or alter the global output-mix Visualizer. `Visualizer(0)` is not guaranteed to work identically on every device.
- Some source apps intentionally block playback capture or use audio usages outside the eligible set.
- The standard Visualizer callback cadence is device-reported; Hop Size cannot force it to match the PCM route.
- The device may clamp the requested Visualizer capture size. The actual applied size is logged.
- The two Android APIs expose different capture formats and scaling behavior. This update brings their level and band mapping closer; exact sample-for-sample parity cannot be guaranteed across OEM implementations.

## Validation performed

- Static review of the Android manifest and capture lifecycle.
- XML/resource integrity check (no resources changed in this audio-only patch).
- Synthetic PCM test: anti-phase L/R content remains non-zero after independent FFT + RMS magnitude combination; pre-FFT mono averaging cancels the same test signal.
- Synthetic calibration check: PCM Hann-bin level after the new scale factor maps to the expected approximate normalized 8-bit Visualizer reference.
- Fixed-Hop logic review: partial `AudioRecord.read()` returns are accumulated until a full Hop block is ready.
- CAPROJ ZIP integrity and metadata validation.

**Not performed:** Android `assembleDebug`, device playback-capture testing, OEM-specific output-mix testing, or listening tests. Those require CodeAssist and a real Android device. The synthetic checks validate the math and data-flow assumptions, not real-device audio quality.
