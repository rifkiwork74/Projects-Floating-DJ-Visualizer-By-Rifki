# V3.0.18 — FFT Resolution and Android Capture Limits

## Scope

This is a research note only. The V3.0.18 UI polish patch does **not** change the FFT default, supported FFT choices, capture routing, or FFT algorithms.

## What the current project implements

- Fresh-install UI preference default: **2048** (`MainActivity.loadSettings`, `fft_size`, fallback 2048).
- Service default: **2048** (`FloatingVisualizerService.DEFAULT_FFT_SIZE`).
- App choices: 1024, 2048, and 4096.
- MediaProjection PCM workspace: clamped to 1024–4096 samples.
- PCM sample rate constant: 44,100 samples/second.
- Android `Visualizer` path: requests the selected value but first reads `Visualizer.getCaptureSizeRange()`, caps to the device maximum, then selects a power-of-two capture size inside that device range. It therefore does not guarantee that the selected UI value is the actual capture size.

## Android Visualizer is device-bounded

Android's public API exposes `getCaptureSizeRange()` for the device's supported minimum and maximum. `setCaptureSize()` requires a power-of-two size inside that range and must be called while the Visualizer is disabled. `getFft()` returns the real/imaginary frequency data for the capture, and the documented frequency of bin `k` is `k × Fs / n`, where `n` is the capture size.

The standard AOSP Visualizer effect header defines `VISUALIZER_CAPTURE_SIZE_MIN` as 128 and `VISUALIZER_CAPTURE_SIZE_MAX` as 1024. That is the standard AOSP implementation ceiling, not a universal promise about all OEM-modified Android audio stacks. The app must continue to trust the range returned by the running device instead of assuming a fixed maximum.

## Project-owned PCM route

The MediaProjection capture path is different from `Visualizer.setCaptureSize()`: it collects PCM samples and runs the project's own FFT workspace. The current implementation only allocates 1024–4096 samples and normalizes values to those three choices. It does not currently accept 8192.

## Resolution and time-window examples

For a sample rate of 44,100 Hz, the approximate bin spacing is `Fs / N`, and the analysis window duration is `N / Fs`:

| N samples | Bin spacing | Window duration |
|---:|---:|---:|
| 1024 | 43.07 Hz | 23.22 ms |
| 2048 | 21.53 Hz | 46.44 ms |
| 4096 | 10.77 Hz | 92.88 ms |
| 8192 | 5.38 Hz | 185.76 ms |

The 8192 row is a mathematical comparison only; it is not a supported app setting in this version.

Larger windows provide finer frequency spacing, which can help distinguish low-frequency components. They also cover a longer span of audio, so rapid changes are represented less immediately. Actual capture cadence, overlap, latency, and CPU cost depend on the capture route and hop/window scheduling.

## Recommendation

Keep **2048** as the fresh-install default for now. It is a practical compromise for general-purpose visualization. 4096 can be useful on the project-owned PCM route when finer low-frequency detail is the priority and device performance is adequate. It should not be assumed to work as a 4096-sample `Visualizer` capture on every phone: the device-reported capture range decides. 8192 should only be considered after deliberately expanding the PCM buffers/FFT implementation, testing processing time and latency on low- and high-end devices, and separately designing a safe fallback for the Android `Visualizer` route.

Do not change the default to the largest number merely because it is available in a UI. The user's target use (fast beat response versus finer spectral separation) matters more than a single maximum number.
