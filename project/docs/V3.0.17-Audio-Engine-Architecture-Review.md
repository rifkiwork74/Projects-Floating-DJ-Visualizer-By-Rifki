# V3.0.17 — Audio Engine Architecture Review

## Scope and evidence

This note describes the audio path present in this project snapshot. It does not claim to have reverse-engineered the internal implementation of another app. The comparison to iJoysoft is limited to features exposed in its public store description and to behavior the user reported; a store listing does not disclose the app's actual Android AudioEffect session, routing policy, DSP coefficients, or vendor integration.

## Current Floating DJ Visualizer EQ path

- `EqEngineService` owns the lifetime of the EQ effect handles and restores the saved working `EqProfile` when the service starts.
- `EqEngineController.activate()` attempts Android `DynamicsProcessing` on API 28+ using a ten-band pre-EQ when the effect can be constructed, grants control, and passes the current InputGain read-back safety check. If that route cannot be controlled safely, it falls back to the device's native `Equalizer` and uses the band count/frequencies the device actually exposes rather than inventing extra bands.
- Optional Android `BassBoost` and `Virtualizer` effects are attempted separately. Their availability and control remain device-dependent.
- The current experiment is attached to output-mix audio session ID `0`, not a session belonging to a player owned by this app. Android's `AudioEffect` documentation describes attaching insert effects to an audio session and marks global output-mix/session-0 use as deprecated. Control may also be taken by another effect; the controller listens for control changes and reports when that happens.
- Preamp is intentionally unavailable on this route. A prior device-level failure pattern involved unstable output/mute behavior on this experimental global route; this release does not write DynamicsProcessing InputGain. Presets may preserve the user's stored Preamp value, but the service turns the unavailable toggle off rather than applying an unverified gain stage.

## Why another EQ may sound more forceful

The user's listening comparison is valid as a report of perceived sound, but it is not enough to attribute the difference to one DSP algorithm. A device can expose a different native band count, center frequencies, hardware DSP, vendor equalizer, loudness compensation, bass enhancement, spatial processing, or media-volume behavior. Two apps that both display a band slider may not control the same effect instance or even the same audio route. `AudioEffect` control ownership can also move between applications/effects.

The public iJoysoft listing advertises a five-band EQ alongside functions such as Bass Boost, 3D Virtualizer, Volume Booster, and presets. That establishes the advertised feature set only; it does not establish whether its booster is a post-EQ gain stage, what session it attaches to, or whether it uses a vendor route. This project can expose a ten-band DynamicsProcessing path on some devices, but on others it falls back to the device's native Equalizer. More visible bands do not by themselves guarantee a stronger or better-sounding result.

To compare fairly, use the same audio source, same device/output, same headphones/speakers, and closely matched perceived loudness; compare one processing feature at a time. Keep playback at a comfortable listening level. A louder result can seem more exciting even when it is not more accurate, and aggressive gain can cause clipping or reduce headroom.

## What “mixer-like” can realistically mean on Android

A true app-owned insert-EQ path is straightforward when the app itself owns the player: create the `AudioTrack`/player, obtain that player's audio session ID, and attach the EQ/DSP to that session. That gives the app a concrete route it owns and can verify.

For other apps' playback, Android's `AudioPlaybackCapture` is a capture API, not a general-purpose insert point into the original app's output chain. It is gated by MediaProjection user approval, audio usage, capture policy, and profile restrictions. It can support an analyzer or a separate captured-audio processing/playback design, but it does not let an app transparently replace every other app's output mixer or bypass those restrictions.

## Safe next-step roadmap

1. Keep the current global output-mix feature clearly labeled experimental and device-dependent; continue capability checks and control-loss handling.
2. Add a diagnostic screen/test matrix for API level, backend selected, actual band centers/count, `hasControl()`, effect implementor, and control-loss events. Do not promise universal global routing.
3. If the app later adds its own music/player source, prototype a player-owned `AudioTrack` session with DynamicsProcessing EQ, MBC, and limiter stages. That is the robust path for an actual app-owned mixer.
4. Any future loudness stage must have headroom accounting, peak/clipping checks, a safe limiter strategy, and bypass/rollback tests. Do not add an arbitrary raw gain boost to the global session-0 route.
5. Treat AudioPlaybackCapture as a permissioned analysis/capture path, not a way to inject effects into every other app.
