# V3.0.18.4 — Horizontal Spectrum Response Recovery

## Baseline and scope

- Baseline: V3.0.18.3 / versionCode 98.
- Release: V3.0.18.4 / versionCode 99.
- Scope: Horizontal 64-band analysis-to-bar mapping and Horizontal source calibration only.
- Preserve the successful V3.0.18.3 Single/DJ behavior, including the 256-band per-profile Hz bank, its bin-width metadata, 55–62 Hz behavior, and independently calibrated PCM range path.

## Observed issue

The device test reported two different Horizontal symptoms:

1. M.Projection ON: selected vocal/low-frequency content could appear held back when other frequencies became strong.
2. M.Projection OFF: Horizontal bars could look excessively active and less proportional to the musical passage.

The same bar height/length value did not explain the difference: the input analysis and capture scaling occur before geometry is drawn.

## Source findings

### 1. PCM Horizontal used full-frame peak normalization

V3.0.18.3 retained the V3.0.18.2 PCM frame-peak gain for the Horizontal bank, even though the Single/DJ bank bypassed that gain. That gain was calculated from the maximum absolute sample anywhere in the full PCM frame and multiplied into every Horizontal band. As the arrangement changed, a loud vocal/cymbal transient could alter the apparent gain of unrelated bass/mid bands.

V3.0.18.4 removes that frame-wide gain from the PCM FFT input. Both Horizontal and Single/DJ now begin from the raw left/right channel FFT magnitudes, while their separate fixed calibration curves remain independent. The existing stereo RMS magnitude combination is unchanged.

### 2. The output-mix route must not globally change scaling mode

Android `Visualizer.SCALING_MODE_NORMALIZED` applies amplification based on captured content; `SCALING_MODE_AS_PLAYED` lets playback volume affect the captured sample/FFT range. Switching this setting globally would also change the already-tested Single/DJ 256-band data, because both banks are decoded from the same capture callback.

Therefore V3.0.18.4 deliberately retains NORMALIZED mode for the output-mix route and shapes only the 64-band Horizontal data with a Horizontal-only exponent (`0.68`). The separately written 256-band Single/DJ bank and the legacy full-range meter slot retain their previous conversions.

### 3. Linear averaging could dilute concentrated notes

A rendered Horizontal bar aggregates multiple bins from the fixed 64-band logarithmic bank. A plain arithmetic mean can suppress a narrow note when only one or two of the sub-bands carry energy.

The Live Display preview, layered Floating Scene renderer, and legacy/root Floating Overlay now calculate a weighted mean and weighted RMS for the bar window, then use `max(mean, 0.75 × RMS)`. This is a restrained energy-preserving floor: broad-spectrum levels where all sub-bands are similar stay close to the mean, while a concentrated note is not diluted as severely. This is not a peak-only detector.

## Data path after the change

### M.Projection OFF

`Visualizer(0)` → normalized Android FFT callback → existing 64-band integration → Horizontal-only exponent curve → shared bar-window aggregation → Live Display / Floating Overlay.

The Single/DJ 256-band conversion remains the V3.0.18.3 path.

### M.Projection ON

User-authorized AudioPlaybackCapture → stereo PCM → independent channel Hann FFT → RMS channel-magnitude combine → no full-frame peak gain → fixed PCM Horizontal calibration (`5.08`) → shared bar-window aggregation → Live Display / Floating Overlay.

The Single/DJ fine bank continues to use its separate fixed scale (`30.0`) and does not inherit Horizontal normalization.

## Explicitly unchanged

- Single/DJ 256-band frequency bank, range sampling, and bin-width-aware measurement.
- Single selected-range calibration and faster Single/DJ attack.
- Horizontal time-based response smoothing and release curve.
- FFT options/defaults, actual device capture-size negotiation, PCM Hop settings, and sample rate handling.
- Bar geometry, dimensions, gaps, effects, colors, glow, profiles/scenes, Android manifest permissions, and audio routes.
- Live Display / Floating Overlay data source and update broadcast contract.

## Static and synthetic validation

- Source scan confirms the PCM Horizontal path no longer calculates or applies `framePeak` / `frameGain`.
- Source scan confirms `calculatePcmFftChannel` uses the raw Hann-windowed channel samples and still combines stereo magnitudes with RMS.
- Source scan confirms the 256-band Single/DJ writer, its scale, its bin-width metadata, and the output-mix Single conversion are retained.
- Synthetic aggregation reasoning: flat sub-band levels produce the same mean/RMS result; concentrated sub-band energy receives a bounded lift rather than being treated as zero or being replaced by the maximum.
- Live Display, layered Floating Scene, and the legacy/root Floating Overlay use the same `max(mean, 0.75 × RMS)` aggregation rule.
- No XML/resource or Android manifest changes were needed.

## Device test requested

Use the same song passage, system volume, profile, bar count, and response value for both capture modes.

1. M.Projection OFF: verify Horizontal no longer jumps excessively during quieter/denser parts and still follows the high vocal ending.
2. M.Projection ON: verify strong vocal and low-frequency content are no longer held down by unrelated high peaks.
3. Compare Live Display and Floating Overlay at the same time; their bar heights should track the same input levels.
4. Recheck Single/DJ at 55–62 Hz and 850–1200 Hz to ensure this Horizontal-only update did not regress the V3.0.18.3 result.
5. Record capture mode, actual FFT size, sample rate, and (for PCM) channel/Hop settings if the two routes still differ.
